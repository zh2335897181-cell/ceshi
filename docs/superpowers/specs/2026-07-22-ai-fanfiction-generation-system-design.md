# AI 同人小说生成系统设计规格

日期：2026-07-22
状态：已完成方案确认，待用户审阅书面规格
产品阶段：本地单用户优先，预留多用户 SaaS 扩展能力

## 1. 产品目标

构建一套由 AI 驱动的长篇同人小说生产系统。用户上传自己有权使用的原作文件，系统解析并理解原作，向用户采访同人创作需求，生成候选企划、故事圣经、全书与分卷大纲，随后持续生成、审校和管理 50 章以上的长篇正文。

系统的核心价值不是一次性生成文本，而是长期维护原作事实、同人设定、人物状态、时间线、伏笔、章节版本和用户决策，使长篇连载保持连续性与可控性。

## 2. 已确认的产品决策

- 原作来源：用户上传或粘贴自己有权使用的内容。网络搜索仅补充公开资料，不抓取盗版全文。
- 目标篇幅：重点支持 50 章以上的长篇连载。
- 用户控制：创建项目时可选择分阶段确认、一次设定全自动或混合托管，之后允许切换。
- 风格能力：支持较强的原作叙事风格相似度控制，并保留风险标签、策略开关和未来投诉处理接口。
- 部署形态：第一阶段为个人本地使用，但所有核心数据均保留 `userId` 和 `projectId`，便于未来升级 SaaS。
- 模型接入：优先使用云端模型 API。用户可配置供应商，并为解析、规划、正文、审校分别选择模型。
- 架构路线：模块化单体配合异步任务引擎，不在第一阶段采用完整多代理微服务。

## 3. 用户流程

### 3.1 创建项目

用户设置项目名称、原作范围、同人类型、目标篇幅、控制模式、模型方案、内容尺度、CP 倾向和结局偏好。系统支持单一作品、系列作品以及多作品联动。

### 3.2 导入原作

支持 TXT、EPUB、DOCX、PDF 和 Markdown。导入流程执行文件解析、章节切分、编码检测、重复检测、缺章与顺序异常检查，并为每个文本片段保存原文件、章节和位置引用。

原始文件、解析文本、外部搜索资料和 AI 生成内容必须分层保存。

### 3.3 理解原作

系统分片阅读原作，逐级生成章节、分卷和全书级知识，提取：

- 人物、关系、性格、动机、能力、口吻与行为边界；
- 世界观、规则、地点、势力、物品和术语；
- 事件、时间线、因果关系和人物知情范围；
- 伏笔、谜团、未解问题与原作结局状态；
- 叙事视角、节奏、语言习惯和对白特征；
- 可用于同人创作的空白时间、支线和剧情分叉点。

每项结论必须保存来源、置信度和版本。AI 推断与原文明确信息分开标记。矛盾或低置信度信息进入待确认列表。

### 3.4 原作报告与用户纠错

系统展示原作知识图谱、人物关系、时间线、风格画像、可创作空间和解析异常。用户修正的内容优先于 AI 提取结果，并形成可审计记录。

### 3.5 AI 采访

系统根据原作和已有回答动态提问，确认同人类型、分叉点、主角、视角、CP、原创角色、必须保留或改变的内容、禁止项、基调、尺度、结局、篇幅、还原度和风格强度。

用户可选择“由 AI 推荐”。此时 AI 必须提供多个方案及影响分析，不能静默替用户做关键决定。

### 3.6 候选企划与故事圣经

AI 默认生成三套差异明确的候选企划，每套包含梗概、卖点、分叉点、主题、主线冲突、角色成长、分卷结构、反转、结局方向、原作一致性风险和预计成本。

用户可以选择、混合或修改方案。确认结果形成故事圣经，包括硬约束、创作自由范围和主动偏离原作的声明。

### 3.7 长篇规划与生产

生产层级为：

1. 全书大纲；
2. 分卷大纲；
3. 主线、感情线、角色线、反派线和伏笔线；
4. 章节卡；
5. 章节草稿；
6. 连续性与人物审校；
7. 自动修订；
8. 用户确认；
9. 运行状态更新。

大纲允许滚动规划。每卷结束时可以根据已确认正文重算后续分卷，但不得未经批准改变终局和硬约束。

### 3.8 修改与影响分析

修改前文时，系统先报告受影响的人物状态、伏笔、大纲节点和后续章节。用户确认范围后执行局部重算，不默认重新生成整本书。

## 4. 系统架构

采用 React 创作工作台、Spring Boot 模块化后端、PostgreSQL、pgvector、本地对象存储适配器和数据库任务队列。耗时任务通过 SSE 返回进度。

前端只依赖稳定的 REST 与 SSE 协议。后端模块不能直接修改其他模块的数据表，只能通过应用服务接口和领域事件协作。未来可以按压力将解析或生成模块拆为独立服务，而不改变前端协议。

建议后端分包：

```text
project
source
knowledge
research
interview
planning
chapter
continuity
workflow
ai
storage
identity
audit
```

产品界面可将流水线表现为原作研究员、同人策划、总编剧、章节作者、角色编辑、连续性编辑和文字编辑。底层仍采用可测试的确定性工作流，而不是让多个自主 Agent 无限对话。

## 5. 核心模块

### 5.1 项目与身份

管理 `User`、`NovelProject`、`WorkflowPolicy`、`ModelProfile` 和 `ApprovalRecord`。本地版使用默认用户，业务数据仍保留用户与项目归属。

### 5.2 原作资产

接收文件，完成切章、清洗、去重、异常检测和溯源。原始文件不可被生成内容覆盖。

### 5.3 原作知识

将片段级提取合并为章节、分卷和全书事实，维护实体、规则、事件、关系、时间线、伏笔、风格和引用。

### 5.4 公开资料研究

通过 `SearchProvider` 查询官方简介、出版方、作者公开资料和可信百科，保存链接、访问时间、摘要与冲突。外部资料不自动覆盖原作事实。

### 5.5 采访与企划

产生 `FanficIntent`、`HardConstraints`、`CreativeFreedom`、候选企划和确认后的 `StoryBible`。保存关键选择及原因。

### 5.6 长篇规划

维护全书、分卷、剧情线和章节卡四级结构。规划必须可版本化，并能追踪与故事圣经的关系。

### 5.7 章节生成

为每章按需组装上下文，生成场景方案与草稿，再完成事实、人物、衔接和语言检查。保存候选版本和变更说明。

### 5.8 连续性与质量

确定性检查覆盖时间、地点、年龄、伤势、物品、能力、死亡状态、知情范围和伏笔状态。模型检查覆盖人物行为、口吻、节奏、重复、情绪与风格。

问题等级为 `BLOCKER`、`MAJOR`、`MINOR` 和 `INFO`。阻塞问题不能自动进入下一章。

### 5.9 模型路由

所有模型调用统一经过 `AIProvider`，提供对话、结构化输出、摘要、嵌入、流式生成、重试、降级、费用和日志脱敏能力。业务模块不得直接依赖厂商 SDK。

### 5.10 异步任务

支持暂停、继续、取消、检查点恢复、分步重试、幂等、优先级、并发限制和实时进度。统一状态为：

```text
PENDING -> RUNNING -> WAITING_APPROVAL -> SUCCEEDED | FAILED | CANCELLED
```

## 6. 长篇记忆模型

### 6.1 L0 原始证据层

保存原作文件、带位置的文本片段、公开网页和用户修正。此层提供可回溯证据，不存放未经标记的 AI 推断。

### 6.2 L1 原作事实层

保存实体、世界规则、事件、因果、时间线和原作结局状态。每条事实携带来源、适用时间、置信度和版本。

### 6.3 L2 同人规划层

保存故事圣经、硬约束、剧情线、大纲树和偏离声明。主动修改原作必须明确记录，不能伪装成原作事实。

### 6.4 L3 连载运行层

保存人物当前状态、关系、伤势、知情范围、同人新增事实、伏笔账本、章节摘要、正文版本和审批状态。

### 6.5 上下文组装

生成章节时只加载当前章节卡、相关原作事实、近期章节摘要、相关远期事实、人物状态和待处理伏笔。上下文应按相关性和强制级别排序，避免反复传输全书。

冲突优先级为：

```text
用户明确修正 > 已确认同人硬约束 > 原作明确事实 > 可信公开资料 > AI 推断
```

## 7. 控制模式与审批

### 7.1 分阶段确认

确认点包括原作报告、创作意图、企划、故事圣经、全书大纲、分卷大纲、章节卡和章节正文。

### 7.2 一次设定全自动

用户确认创作意图和故事圣经后，系统执行到预设目标。内部质量门仍然生效，严重冲突不能标记为成功。

### 7.3 混合托管

用户设置自动运行到第几章、每隔多少章暂停、风险阈值、预算阈值和人物偏离阈值。模式切换只影响后续任务。

## 8. 自动修订与失败恢复

每次修订保存前后版本、问题、修改范围、模型、提示词版本、费用和耗时。单章最多自动重写三次，仍有阻塞问题时进入人工等待，避免无限消耗。

恢复策略：

- 网络超时：指数退避；
- 模型限流：等待、切换备用模型或暂停；
- 结构化输出错误：修复一次后重新请求；
- 上下文超限：移除低相关资料后重组；
- 余额或预算不足：暂停并展示预计费用；
- 文件失败：隔离问题文件，不回滚成功章节；
- 服务退出：从最近检查点恢复；
- 用户取消：保存已有产物，不提交未完成状态。

## 9. 数据与接口

主要领域对象包括：

- `User`、`NovelProject`、`WorkflowPolicy`、`ModelProfile`；
- `SourceAsset`、`SourceChapter`、`SourceFragment`；
- `CanonEntity`、`CanonFact`、`CanonEvent`、`CanonRelation`；
- `FanficIntent`、`Proposal`、`StoryBible`、`DeviationDeclaration`；
- `OutlineNode`、`PlotThread`、`ChapterCard`、`ChapterVersion`；
- `CharacterState`、`StoryFact`、`Foreshadowing`、`ContinuityIssue`；
- `GenerationTask`、`ApprovalRecord`、`AuditRecord`、`UsageRecord`。

核心 API：

```text
POST   /api/projects
GET    /api/projects/{id}
PATCH  /api/projects/{id}
POST   /api/projects/{id}/sources
POST   /api/projects/{id}/source-analysis
GET    /api/tasks/{taskId}
GET    /api/tasks/{taskId}/stream
GET    /api/projects/{id}/canon-report
PATCH  /api/projects/{id}/canon-facts/{factId}
POST   /api/projects/{id}/canon-report/approve
GET    /api/projects/{id}/interview/next
POST   /api/projects/{id}/interview/answers
POST   /api/projects/{id}/proposals
POST   /api/projects/{id}/proposals/{proposalId}/approve
GET    /api/projects/{id}/story-bible
PATCH  /api/projects/{id}/story-bible
POST   /api/projects/{id}/story-bible/approve
POST   /api/projects/{id}/outlines
POST   /api/projects/{id}/chapters/{chapterId}/generate
POST   /api/projects/{id}/chapters/{chapterId}/review
POST   /api/projects/{id}/chapters/{chapterId}/approve
GET    /api/projects/{id}/continuity/issues
POST   /api/projects/{id}/impact-analysis
POST   /api/projects/{id}/exports
```

耗时接口返回 `taskId`，客户端通过 SSE 获取进度。任务创建必须使用幂等键，避免重复扣费和重复写入。

## 10. 技术选型

- React、TypeScript、Vite、Tiptap；
- Spring Boot 3、Java 21；
- PostgreSQL 与 pgvector；
- 本地目录实现 `ObjectStorage`；
- 数据库任务表与 Spring Worker；
- SSE 实时进度；
- Docker Compose 本地部署；
- Apache Tika 与独立格式适配器；
- OpenAI、Claude、Gemini、DeepSeek 等 `AIProvider` 实现。

第一阶段不引入 Redis、RabbitMQ、独立向量数据库或微服务。未来按并发和运维需要替换接口实现。

现有 `novel-workbench` 原型使用 MySQL 初始化脚本和内存模拟仓储。正式实现以 PostgreSQL 与 pgvector 为目标数据层：沿用现有 DTO、Controller 和前端协议，重新实现持久化接口并编写一次性示例数据迁移脚本；不要求同时长期维护 MySQL 与 PostgreSQL 两套实现。

## 11. 安全、隐私与版权

- 用户确认其拥有上传和使用内容的权利；
- 不主动抓取盗版全文；
- 云模型调用前告知原作片段会被发送给供应商；
- API 密钥本地加密保存，不进入普通日志；
- 日志记录片段 ID 和哈希，不记录大段原文；
- 删除项目时删除原文件、索引、摘要、缓存和生成内容；
- 所有编辑与审批保留审计记录；
- 预留原作与作者风险标签、作者禁用名单、投诉、冻结与下架接口；
- 预留公版作品与受版权保护作品的不同风格策略。

## 12. 测试方案

### 12.1 单元测试

覆盖文档切章、编码识别、事实版本、冲突优先级、人物状态、伏笔状态、任务状态机、预算和重试上限。

### 12.2 集成测试

覆盖上传到知识库、模型适配器、SSE 重连、检查点恢复、项目完整删除和前文修改影响分析。

### 12.3 AI 评估集

使用有权使用的作品与人工标注答案，评估实体与事件提取准确率、引用正确率、人物还原度、状态冲突率、伏笔回收率、重复情节率和硬约束遵守率。

模型、提示词或检索策略变更后必须运行固定回归集。提示词必须版本化。

## 13. 实施阶段

### 阶段一：原作理解底座，3 至 5 周

实现项目、模型配置、文件导入、解析任务、原作知识库、引用报告和用户纠错。验收条件是完整导入一部长篇，并能用原文引用回答人物、事件和设定问题。

### 阶段二：同人企划与规划，3 至 4 周

实现动态采访、候选企划、故事圣经、全书与分卷规划、章节卡和三种控制模式。验收条件是生成一套支持 50 章以上的可确认规划。

### 阶段三：章节生产闭环，4 至 6 周

实现上下文组装、章节生成、版本、审校、自动修订、审批和运行状态更新。验收条件是连续生成至少 20 章且无严重人物、时间线和知情范围冲突。

### 阶段四：长篇稳定性，3 至 5 周

实现影响分析、局部重算、暂停恢复、模型降级、成本控制和 DOCX、EPUB、Markdown 导出。

### 阶段五：SaaS 预备改造

实现正式身份认证、租户隔离、云对象存储、队列、计费、内容审核、投诉和发布适配器。第一阶段仅保留边界和字段，不提前实现。

## 14. 非目标

第一版明确不实现：

- 自动抓取盗版小说全文；
- 自动发布到外部小说平台；
- 支付、订阅、团队协作和公开社区；
- 一次性无检查地生成整本正文；
- 无版本记录地覆盖已确认章节；
- 为未来规模提前建设微服务、消息中间件和复杂租户系统。

## 15. 第一版成功标准

- 用户能上传并解析一部长篇原作；
- 原作知识有出处、可信度、版本且可纠正；
- AI 能根据原作动态采访用户并生成差异化企划；
- 系统能生成 50 章以上的分层规划；
- 系统能连续生成、审校、确认和管理章节；
- 每章确认后更新人物、事实、时间线和伏笔；
- 模型可配置，成本可预估、追踪和限制；
- 长任务可以暂停、恢复和局部重试；
- 本地版本可用，未来 SaaS 化无需推翻核心领域模型。
